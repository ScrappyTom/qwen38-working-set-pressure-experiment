## 3. Operational capacity if source selection changes; coordination limit

**Accounting separately for requests and actions.**

- **Requests:** 2 remaining. This response is one. After it, **1 request** remains.
- **Actions:** 6 remaining. A bare `patch` costs 1 action. A `patch` + `check_after` costs 2. A `work_on`, `read`, `reopen_event`, `reopen_result`, `search`, `tree`, or `p0_page` each costs 1.

**What one response can carry.** Per the system message, a response selects either:

- one `operation` (any single action form), or
- one `PATCH` **plus** its `"check_after":"public"` (two actions).

It cannot carry two independent patches, nor a `work_on` followed by a `patch`, in the same response.

**The task requires two file edits.**

1. `Lib/test/test_configparser.py` — the recovered proposal.
2. `Doc/library/configparser.rst` — runnable examples for both interpolation modes (not yet drafted; the current RST at lines 334–425 and 1352–1380 documents the interpolation classes and the exception stubs but contains no missing-reference example, no `raw=True` contrast, and no "supply the missing setting" walkthrough).

Two edits require two patch-bearing responses, hence **two requests**. After this response, only **one request** remains.

**What `work_on` would do to the proposal.**

The patch specification requires the `old` text to be "visible before editing," either in the current working set or in a complete read/group result whose bytes and fingerprint still match. The current working set contains the test-file tail (lines 2200–2212), which includes the `old` text. A `work_on` **replaces** the entire working set. If a new `work_on` selected only the RST ranges (for the documentation edit), the test-file tail would be released. The `old` text would no longer be in the working set.

To re-apply the test patch after such a `work_on`, one would need to either:

- include the test-file tail in the same `work_on` (possible: `work_on` accepts up to 16 source ranges), or
- issue a separate `read` of lines 2200–2212 (1 action).

The `work_on` route is costless in extra actions (it is the one operation for that response). The `read` route costs 1 action but preserves the RST ranges already in the set. Either way, the proposal's `old` text can be re-established. The archive handle `EVT-0071` always retains the full patch bytes via `reopen_event`, so the proposal itself is never lost.

**The concrete coordination limitation.**

The binding constraint is the **request count**, not the action count. Six actions are available; the two patches plus a final check need only 4 (two patches + one check, or one patch + check + one patch + check = 4). The actions are sufficient.

But the **one-patch-per-response** rule means two file edits need two responses. With one request left after this response, only one of the two edits can be issued. The second edit has no request to carry it. The public check (which must validate the candidate containing *both* edits) cannot pass after only one edit. Submission requires a passing check on the current candidate.

If this response is discussion-only (as instructed), it consumes the remaining request and **ends the attempt without submission**. The recovered proposal stays in the archive at `EVT-0071`; no edit is committed; the candidate is unchanged. The RST documentation remains unextended.

If instead the response issues the test-file `patch` (1 action) or `patch` + `check_after` (2 actions), it uses the last request. The test edit is committed (or committed + checked). The RST documentation patch has no remaining request. The attempt ends after that response—either with the test-only candidate (if no check) or with a check result on the test-only candidate (if `check_after` was requested). In neither case can the RST edit be applied, and the contribution is incomplete.

**Consequence.** The existing operation forms and their per-response limits, combined with the remaining request budget, do not permit both required file edits to be issued. The interface does not offer a batch-patch form, a multi-file `patch`, or a mechanism to attach two `check_after`-eligible edits to one response. The limitation is one of **request-to-operation cardinality**: the task's two-edit scope exceeds the one-edit-per-response capacity available in the remaining budget. Retaining the interface as defined, the consequence is that this particular checkpoint (2 requests, 6 actions, two required edits) cannot reach a passing check and submission within its own limits. No source-selection change via `work_on` alters this conclusion, because the `work_on` itself occupies the single operation slot of a response and cannot be paired with a `patch` in the same response.
