## 2. What the saved capacity rejections establish; what would require a new host measurement

**Established (known from the records):**

- Both patches reached the host's capacity gate and were rejected before any commit. The host states explicitly: "no edit committed."
- The failure mode is a combined-size overflow: the serialized edit plus the "refreshed working material" (the source pages and saved results that would be attached to the next input) exceeded the host's next-input capacity.
- The host's remedy is procedural, not substantive: "Select a narrower relevant working set with work_on." This implies the edit content itself may be fine; the surrounding working set was too large.
- The `candidate_limits` in the workspace (`max_file_utf8_bytes: 1048576`, `max_total_utf8_bytes: 8000000`, `max_line_utf8_bytes: 512`) are the static bounds. The dynamic constraint is the per-input budget the host enforces.

**What is NOT established / would require a new host measurement:**

- The exact byte size of the rejected `old` + `new` patch text. The rejection message does not report a numeric overflow or a size budget. The system prompt states the host "validates complete UTF-8 sizes … before committing; it never shortens an edit" and that "these are host limits, not a request to manually count or split text." The agent cannot compute whether a given patch will fit.
- Whether a narrower `work_on` source selection (fewer lines, fewer saved results, or one file instead of two) would bring the same edit under the capacity. The host does not return a residual budget.
- Whether the edit content is correct. The rejection is purely a size gate; it says nothing about whether `old` matches the current file or whether `new` is semantically right.

In short: the rejections prove a sizing conflict at the host, not a content error. The only way to learn whether a revised working set + edit will fit is to attempt it and observe the host's response.
