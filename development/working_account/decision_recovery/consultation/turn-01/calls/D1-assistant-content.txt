## 3. Distinguishing eligibility from edit-fit and task-adequacy

These are three independent gates:

| Gate | What it asks | Relevant limit / criterion |
|---|---|---|
| **Eligibility (old-source visibility)** | Does the host have a qualifying result that contains the exact `old` bytes, with a matching fingerprint? | "complete retrieved read/group result" vs. "partial saved-result page"; fingerprint match |
| **Capacity (action size)** | Does the serialized `patch` action fit within the host's byte limits? | ≤ 65 536 UTF-8 bytes per fragment; ≤ 1 048 576 serialized bytes per action |
| **Task adequacy (content correctness)** | Does the `new` text correctly implement the required regression coverage and documentation? | Task requirements, actual behaviour, check scopes |

A patch can fail any gate independently of the others. The "partial saved-result pages do not" clause speaks only to the first gate. It says nothing about whether the proposed edit is too large, whether it meets the port-coverage spec, or whether it preserves existing tests.

## 6. Is there a specific operational ambiguity, and what is the consequence?

**The distinction is resolvable from the complete description, though it is not immediately obvious.**

The key phrase is *"partial saved-result pages."* Two readings are possible:

- **(a) Archival reading.** "Saved-result" = an archived `RES-…` handle. A "page" of it (obtained via `reopen_result`) is partial by construction. A `read` or `work_on` result is a *live, complete* page chosen by the host to fit the next input and is **not** a "saved-result page." Under this reading, the current test-file selection (lines 1–800, returned by the initial `work_on`) is a **complete retrieved group result** and **does qualify**.

- **(b) Broad reading.** Any result that is a *page* of a longer file (i.e., `next_start_line` points past the returned end) is "partial" and does not qualify. Under this reading, the current selection is ineligible, and the model would need to re-read the entire file in one page (or the full file must fit in the next input) before patching.

The complete description supports reading **(a)**:

- `work_on` says the host "sizes source pages together" and "includes each requested saved record in full, or rejects the group." The result is a successfully assembled, host-verified page — a *complete retrieved group result*.
- `read` says "The host chooses a whole-line page that fits the COMPLETE next input." Again, a complete, host-sized page.
- `reopen_result` explicitly pages through a saved blob: "offset=0 starts; continue with returned next_offset. … A later page replaces the earlier page of the same handle." This is the only operation that produces *partial pages of a saved result*.
- The phrase "saved-result pages" pairs "saved" (archival) with "result" (the `RES` handle) and "pages" (the pagination of that handle). It does not say "partial *source* pages" or "incomplete *file* views."

Under reading (a), the `next_start_line: 801` in the working-set entry is a **navigation aid** ("if you want more, continue from line 801"), not a marker that the result is "partial" in the eligibility sense. The result is complete *as a result*: the host returned exactly what it sized to fit.

**The consequence of the ambiguity (or the model's apparent uncertainty about it):**

The model's thinking shows it leaning toward reading (b), concluding "partial saved-result pages do not qualify" for the current 1–800 selection, and considering an unnecessary re-read or re-selection to "be safe." If the model acts on reading (b), it will:

1. Consume an action on a `work_on` or `read` to re-establish source visibility that it already has.
2. Risk a second capacity rejection if the re-selection is too broad.
3. Delay the actual `patch` by one or more operations, consuming from the 59-action allowance and the 19-request budget.

The consequence is **not a wrong outcome** — the model will still arrive at a valid patch — but it is **inefficient**: it spends operations resolving an eligibility question that the complete description already answers in favour of the current selection. No change to the interface is needed; the description, read as a whole, distinguishes live `read`/`work_on` pages from `reopen_result` archival pages. The model's uncertainty is a reasoning step it can resolve by re-reading the three action descriptions side by side, which it can do without consuming an action.
