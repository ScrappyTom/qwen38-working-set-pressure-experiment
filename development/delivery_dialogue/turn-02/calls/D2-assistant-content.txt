### Concrete contribution: correct `UnarySimplifier.visit_UnaryOp`

The current faulty behavior is visible in the supplied source:

```python
        if isinstance(node.op, (ast.UAdd, ast.USub)):
            return ast.copy_location(node.operand, node)
        return node
```

That code removes both unary plus and unary minus by replacing the `UnaryOp` node with its operand. That is too broad.

A supported patch would replace only this fragment:

```python
        if isinstance(node.op, (ast.UAdd, ast.USub)):
            return ast.copy_location(node.operand, node)
        return node
```

with:

```python
        if (
            isinstance(node.op, ast.UAdd)
            and isinstance(node.operand, ast.Constant)
            and type(node.operand.value) in (int, float)
        ):
            return ast.copy_location(node.operand, node)
        return node
```

That preserves the required contract as stated in the README:

- eliminates unary plus on exact built-in integer and float literals;
- does not eliminate unary minus;
- does not fold or remove unary operators on non-literal operands;
- preserves negative zero, because `-0.0` is `USub` applied to a constant;
- preserves user-defined unary dispatch for non-literal operands;
- leaves the rest of the module structure untouched.

## Assessment of current presentation and operating rule

I would **retain** the current presentation and operating rule as the baseline.

The current design correctly distinguishes:

- durable storage of exact payloads;
- inclusion of payload bodies in the next input;
- successful tool execution;
- useful work from the admitted input;
- historical recovery by handle;
- current-source version protection.

It also preserves exact historical recovery:

- `RES-xxxx` can recover saved result bodies;
- `OBS-xxxx` can recover saved observation bodies;
- hashes and sizes identify the exact recovered payload;
- candidate and file guards still protect edits;
- a historical read remains applicable if the file has not changed.

No replacement terminology or general memory architecture is required.

### Demonstrated limitation

The demonstrated limitation is narrow but real:

- The all-external input in the earlier state was 12,688 tokens.
- A state retaining only the newest body was 16,218 tokens and was rejected by the 16,000-token working-set limit.
- In the later C02-like state, even all payloads external required 16,154 tokens.
- A useful BUILD-A report group cost 20,171 tokens.
- A both-builds group cost 23,695 tokens.
- The maximum admitted input is 23,808 tokens.

So the current 16,000-token input working-set limit is below the maximum admitted input and below later all-external states that still retain the full ordered event signal.

That is the important distinction: this is not a failure of exact custody, handle recovery, or version protection. It is a capacity threshold issue.

### Unresolved capacity choice / one narrow change

The unresolved capacity choice is whether the 16,000-token input working-set limit should remain binding even when the state is within the already-documented maximum admitted input of 23,808 tokens.

If one narrow change is allowed, I would propose:

> Raise the input working-set admission threshold to the already-documented maximum admitted input of 23,808 tokens, while retaining the existing externalization rule.

That would mean:

**Included**

- all resident event signals;
- ordered event records;
- current candidate ID;
- current P0/root information;
- task text;
- tool contract;
- observation directory entries;
- result handles and payload identities;
- file/candidate version guards;
- call-budget state;
- exact recovery references.

**Omitted**

- exact payload bodies beyond the admitted working set.

Those omitted bodies would still be recoverable through their existing handles.

**Preserved protections**

- `patch` would still require the current pre-edit candidate and file SHA.
- A historical file SHA remains usable only while the file remains unchanged.
- `reopen_result`, `reopen_observation`, and `reopen_event` would still recover exact saved payloads without re-executing operations.
- Hashes and sizes would still verify the recovered bodies.
- An accepted patch would still return a new candidate and file fingerprint.
- Check state would still be cleared by mutation and updated only by accepted check results.

This proposal does not invent a new tool, handle, or retention system. It only aligns the input working-set threshold with the already-documented maximum admitted input.

If no such change is adopted, then the current rule should be treated as having an unresolved capacity constraint: the full ordered event signal may eventually exceed the 16,000-token working-set limit even when every payload body is external.

## Observation that would show whether the proposal helped

A preference for a larger working set would not be enough.

The useful observation would come from actual contribution-and-continuation work:

1. **Admission succeeds in the previously blocked state**

   A C02-like state with all payloads external and a token cost above 16,000 but below or equal to 23,808 is admitted instead of rejected.

2. **A saved contribution is made in that continuation**

   For example, a patch to `compiler/unary.py` is accepted using the existing candidate and file guard, and the result returns the previous/current candidate IDs and the new file fingerprint.

   Or, in a later step, a report patch to `reports/incident.json` is accepted after the relevant observations have been reopened.

3. **Exact recovery remains usable**

   A subsequent `reopen_result`, `reopen_observation`, or `reopen_event` returns the same exact payload identity, hash, and size, or recovers source needed to validate the next edit.

4. **Version protection still works**

   The next edit still uses the correct pre-edit guard. If a patch has occurred, the guard used is the one produced by that patch, not an older expired guard.

5. **The check path remains meaningful**

   A public check can be admitted and produce an accepted result, even if `passed=false` because the report is still incomplete. After the report is completed, the same mechanism can be used to determine whether the full candidate passes.

If, by contrast, the >16,000-token all-external state remains rejected, or the only way to proceed is to delete the ordered event frame, discard version guards, or treat a reopened body as something other than exact historical recovery, then the proposal has not helped.
