One small change would be to add a single **episode annotation** beside the existing report text, explicitly separating the report from the session’s repair attempt.

### Proposed concrete change

Beside `active_user_authored_step.text`, add one annotation, for example:

```json
"active_user_authored_step": {
  "host_inference": false,
  "id": "ECOLOGICAL-REPAIR",
  "text": "An accepted edit to a Python artifact is followed by a failed reopen of the edited function. ...",
  "episode_annotation": "Pre-session report. EVT-0011 is this session's attempted repair; it is not a new report or a behavioral check."
}
```

Equivalently, as a UI annotation:

```text
active_user_authored_step.text:
  “An accepted edit to a Python artifact is followed by a failed reopen of the edited function. ...”

Episode annotation:
  Report: pre-session.
  EVT-0011: this session's attempted repair; not a new report or behavioral check.
```

This uses the existing record and does not introduce a new handle system, event, result, or storage concept.

### What that would make explicit

From that annotation, one could conclude:

1. **The report is prior to the supplied repair session.**  
   The report is not a new observation made after the session’s actions.

2. **EVT-0011 is not the reported failure itself.**  
   EVT-0011 is the actor’s attempted repair during this session.

3. **The repeated task text does not create a new failure after the patch.**  
   The fact that the same report appears in `task` and `active_user_authored_step.text` would not be read as evidence of a post-patch reopened failure.

4. **The concrete repair evidence remains the accepted patch.**  
   The current candidate is still identified by `current_p0.candidate_id`, and the concrete recorded change is still in EVT-0011, with its diff at:

   ```text
   active_phase_event_frame.events[10].result_body.fields.diff
   ```

5. **No additional whole-file read is required merely because the candidate identity changed.**  
   The pre-patch read plus the accepted exact patch can reconstruct the successor source where needed. The missing item is behavioral verification, not source availability.

### What would still remain unestablished

Even with that annotation, the input would still not establish:

- whether the attempted repair actually fixes the reported behavior;
- whether the current candidate preserves unchanged-content behavior;
- whether later updates behave as required;
- whether genuinely stale references are still rejected correctly;
- whether `check public` has been run on `current_p0.candidate_id`;
- whether any check passed;
- whether the candidate is the final candidate;
- whether submission has occurred.

In short, the annotation would close the **report/repair-episode ambiguity** without pretending to close the **behavioral verification gap**.
