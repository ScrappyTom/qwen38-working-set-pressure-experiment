# Coding-run notes for project governance

These are observations from one completed coding lineage, not general performance
guarantees. Detailed prompts/replies/effects are covered in RUN001-READING_NOTES.md
and RUN001-RESULTS.md; source custody and artifact checks are separate.

* Completion means useful saved code, meaningful tests, preserved earlier work,
  accurate accompanying documentation, actual verification and checked submission.
  The continuation supplies that result. It is not a fresh 24-request solution:
  include the stopped nine-request attempt and its erroneous checker requirement.
* Checkers must not add an exact message/API contract absent from the task. Qualify
  an alternative correct implementation, not only a reference patch. Preserve the
  original invalid assertion/run and declare the corrected checker before resuming.
* Read the actual decision input before diagnosing repeated acquisition. C20 lacked
  the earlier zero-match result; C24 lacked the already-found exception-location
  result. Exact recovery is legitimate when the relevant fact is no longer visible.
* A small recovery input can restore operability while unnecessarily dropping
  useful navigation. Correcting that specific omission does not require semantic
  summarization, mandatory accounts or another information taxonomy. Keep a bounded
  fallback so optional navigation cannot block actual error/check feedback.
* Recovery inspection can support editing/checking/closure without work_on. Report
  what the actor actually did; do not credit model-selected group replacement.
* A model account may be useful and later stale. At closure, current source and an
  applicable observation overrode an obsolete note correctly. Do not silently
  rewrite model-authored meaning or treat a note as source/check authority.
* Include host sizing in cost. Four near-capacity acquisitions cost 278.939 seconds
  of processing here. All 167 native measurements were distinct, so identical-input
  memoization is not an evidence-based remedy for this run. Do not call all latency
  overthinking or present a scripted shorter route as measured savings.
* The owner prioritizes coding. Use the observations to improve the coding host and
  complete substantive code changes; detailed coding reports remain appropriate.
  Synthetic reading/paper tasks stay deferred without rewriting their status.
