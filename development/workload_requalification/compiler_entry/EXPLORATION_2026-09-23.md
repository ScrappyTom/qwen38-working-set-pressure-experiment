## The current boundary is more than one missing schema entry

1. [Working-view schema](../../../src/working_set_exp/working_view.py) explicitly removes `reopen_observation` from the older continuation schema. The [decision view](../../../src/working_set_exp/decision_view.py) builds on the current operable schema, so its reply grammar and reference do not offer the legacy operation. The current model would not be told how to request `OBS-0001`.
2. [WorkingSession._ordinary](../../../src/working_set_exp/working_session.py) creates a fresh `ToolExecutor` for each ordinary action without a `reopenable` registry. The older [executor](../../../src/working_set_exp/tools.py) knows how to return an imported observation, but that alone does not attach the sealed compiler captures to this session. Adding an action form alone would therefore produce an unavailable-handle rejection.
3. Current `WorkingSession.execute` gives dedicated, measured paging to `RES` and `EVT`, and `work_on_exact` can retain complete saved `RES` records beside source. It has no dedicated `OBS` selection path. A successful imported-capture operation could create an ordinary `RES` receipt; after that, the existing archive and selection machinery may suffice. That is a candidate design to qualify, not a demonstrated fit.
4. Current check observations use `CHK` addresses and `inspect_observation` for captured checker streams. Those observations concern a particular checked candidate and checker. The compiler's `OBS` records concern the original incident candidate. The two kinds need different labels in the actual view even though both are stored evidence.

The existing [compiler entry plan](ENTRY_PLAN.md) correctly identifies the missing access route. My added conclusion from tracing execution is that the bridge has to span **inventory, reply schema and decoder, session execution, result custody, and the measured next input**. A task-local session adapter looks sufficient for the first qualification. I see no evidence yet that a new global evidence type, account graph, or mandatory planning object is needed.

## Proposed qualification boundary

Start with the three sealed captures and an immutable, task-local inventory: handle, descriptive target, original candidate binding, exact byte count/digest, and a plain statement that these are historical incident records. Inventory is navigation; it must not claim the bodies were presented. Reuse the meaning of `reopen_observation` if the effective native reply schema, grammar, validator, operating reference, and session executor all agree. Do not copy the legacy stage gate or result-size wrapper merely because the name is reused.

On a valid request, load the named original bytes, verify the manifest binding, archive the actual acquisition as a new operation/result pair, and expose its new `RES` address. Keep the `OBS` address as the canonical source of the historical record. The receipt should distinguish **acquired**, **shown in this input**, and **shown completely**. This matters because the current host can preserve a read-only result while reducing immediate feedback to status when the complete next input will not fit. If that happens, the actor needs an explicit `RES` recovery route; accepted acquisition cannot be presented as completed reading.

First measure these exact paths with the current native interface: one returned capture in ordinary view; each capture after a source edit; all three full `RES` records together; the same group with the relevant current compiler source and report; and a crowded or recovery input. The captures total 27,576 original bytes before receipt wrapping, source, history, and prompt structure. That byte sum is **not** a token-fit result. `work_on_exact` should either admit each requested complete record or preserve the old selection and say which requested group did not fit. Existing `reopen_result` paging may support serial inspection if a joint group fails; a page must show its actual extent and must not be described as a complete tree.

Useful focused cases before any model call:

| Case | Mechanical assertion |
|---|---|
| Discovery | Three correct historical labels and bindings appear; no expected report or reference repair appears. |
| Retrieval and restart | `OBS` bytes and digest equal the sealed record, and the same handle still resolves after reconstruction. Unknown, corrupt, or unavailable records fail explicitly. |
| Interface agreement | Native grammar accepts exactly the advertised reply; decoder, validator, session action rule, and execution agree. |
| Delivery | A stored acquisition omitted from the next input is labeled as omitted, has a usable `RES` address, and can be recovered without inventing a past action. |
| Selection | Two captures plus relevant current source are either complete in the measured input or rejected without a partial-success label or lost prior selection. |
| Version boundary | A later compiler edit does not rebind historical captures; an earlier check retains its own candidate/checker identity. Imported bytes never authorize a source edit. |
| Scripted contribution | A separately labeled actor-independent route acquires, edits, checks, writes the report, consumes feedback, and submits under the actual operation forms. This proves host feasibility only. |

The full scripted route should use the exact original checker and keep its evaluator-side answer inaccessible to the actor. A public pass still calls for independent review of report meaning and source preservation. Only after this host path is qualified should an uncoached, finite original-entry run be declared. The saved-report continuation starts from an assisted optimizer repair and remains a different ledger entry.

## What I would defer

The current [working account](../../../src/working_set_exp/accounted_contribution.py) already records authored text and exact action provenance; it does not certify the text's claims. A source-linked account experiment is interesting after a verified compiler reference trajectory exposes a real switch between repair and report work. I would freeze an actual transition state, compare a continuation retaining exact evidence with one using an actor-written account plus recovery routes, and then use a fresh full task. I would first check whether the account loses a proposition that was available, whether evidence was absent, or whether the actor misread present evidence. Those are different failures. No source-linking patch is earned solely by the three-capture task description.

The [apparatus profile plan](../apparatus_profile/PLAN.md) and [call-boundary inventory](../apparatus_profile/CALL_BOUNDARIES.md) already separate repeated validation during sizing from checks before dispatch and execution. I agree with keeping that work separate. The inventory still calls out dynamic reads and callback paths to trace, so a claimed neutral optimization would be premature. If batching is later qualified, its detection timing and executed effects should be compared explicitly; identical happy-path request bytes are insufficient.

**Next decision:** qualify the smallest task-local capture adapter against the actual current decision view and exact native input. If the complete record and selection routes fit and preserve truthful delivery, proceed to the original compiler entry. If they do not, identify the measured failing transition before adding another evidence representation or changing context policy.
