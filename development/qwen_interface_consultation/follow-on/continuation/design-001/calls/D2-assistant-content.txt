I would keep the current interface and event-frame names, but I would add a compact model-facing **next-action decision frame** above the raw event frame. The hidden `response_format` can remain the machine guard, but the prompt should also expose the argument contracts, binding meanings, and effects in a stable, readable form. I am not performing the embedded coding task or emitting a tool action.

## Preferred shape

I would present three layers:

1. **Decision frame**
   - current candidate
   - current file guard for the relevant path
   - current check state relative to that candidate
   - current source-read state relative to that candidate
   - call budget
   - short ordered-event summary
   - recovery handles

2. **Action contracts**
   - required arguments for each available action
   - accepted forms
   - what each binding means
   - what the action does and does not do

3. **Recovery layer**
   - saved result/event handles
   - what each handle contains
   - explicit note that reopening is access, not execution or currentness

The main improvement is not a new memory system; it is a presentation boundary between **facts that decide the next action**, **facts that can be reopened on request**, and **audit details that should not compete with the decision frame**.

  effect: retrieves a listed saved observation envelope; no rerun; creates a new ordered access event.

  handle: `RES-` followed by 4 digits
  effect: retrieves the saved exact operation result envelope with original bindings and body; no rerun; creates a new ordered access event.

reopen_event {handle}
  handle: `EVT-` followed by 4 digits
  effect: retrieves the saved exact action payload fields; no edit; creates a new ordered access event.

## What I would show together

I would keep these visible in the normal decision frame:

- **Current candidate identity**
  - The next `check`, `submit`, or `patch` guard depends on this.

- **Current file hash for the relevant path**
  - Needed for `expected_file_sha256` on a future patch.
  - In this state it comes from the latest patch result.

- **Current check state relative to the current candidate**
  - The last `public` check was on the predecessor candidate, not the current candidate.
  - This distinction is decision-critical.

- **Current source-read state relative to the current candidate**
  - A historical read of the old candidate does not satisfy a future requirement to read the current source.

- **Ordered event summary**
  - `read`, `check`, and `patch` in sequence.
  - The exact predecessor/successor candidate and file bindings should remain visible.

- **Recovery handles**
  - `RES-0001`, `RES-0002`, `EVT-0003`, `RES-0003`.
  - Short labels of what each contains.

- **Action contracts**
  - Required arguments, accepted forms, binding meanings, and effects.
  - Especially the distinction between `check` as execution and `reopen_result` as retrieval.

- **Call budget**
  - `calls_remaining` is directly relevant to action planning.

## What I would leave available on request

I would not show these inline by default:

- **Exact saved read page from `RES-0001`**
  - It is historical source for the predecessor candidate.
  - Useful if the model needs to compare historical source, but it does not make current source read.

- **Exact check stdout/stderr from `RES-0002`**
  - The decision frame can show `passed=true`, sizes, and result handle.
  - The exact stdout text should be reopened only if needed.

- **Full patch payload/diff body**
  - The short old/new strings are enough for the decision frame.
  - The exact diff is recoverable through `RES-0003` and the event handle `EVT-0003` for the action payload.

- **Full P0 pages, tree pages, or search pages**
  - These are structure/current-source access operations, not terminal decision facts in this state.

- **Full saved observation envelopes**
  - Currently `observation_directory.entries` is empty, so none are relevant.

- **Full canonical payload hashes/sizes for every field**
  - Useful for custody audit, but not normally needed to choose an action.

## What I would keep as internal audit detail

I would keep these out of the main decision frame unless an audit problem arises:

- `exact_pair_identity` hashes and sizes
- payload-level `sha256`/`size_bytes` for non-resident canonical JSON
- `event_frame_verification` counts
- `host_sufficiency_judgment`
- `semantic_ranking`
- `latest_transition_binding`
- `active_user_authored_step.host_inference`
- `fixture_id`
- `reconstruction_notice` in full prose form, unless compressed into the short `NOTICE` block
- `one_action_result_identity_per_sequence`
- detailed residency-contract prose

However, I would **not** remove the handles, schema versions, ordered sequence, or exact binding hashes needed for recovery and guards. Those are not merely audit; they are operational custody.

## Presentation preferences

These are my design preferences, not implementation facts:

- I prefer to see **current-candidate state** separately from **historical event state**.
- I prefer to see whether a check or read applies to the **current candidate** rather than only seeing that a check/read occurred.
- I prefer to keep **recovery handles** visible without showing their full bodies by default.
- I prefer to keep **action contracts** visible even if the machine `response_format` is supplied separately.
- I prefer to keep the ordered event sequence visible, not replace it with a semantic summary.
- I prefer to keep the distinction between:
  - executing a new `check`,
  - executing a new `read`,
  - executing a new `patch`,
  - retrieving a saved `check` result,
  - retrieving a saved `read` result,
  - retrieving a saved `patch` payload.

## Uncertainty

These are uncertain or under-specified for a pure presentation solution:

- The state does not show whether `public` would pass on the **current** candidate.
- The state does not show the exact check stdout/stderr text without reopening `RES-0002`.
- The state does not show the exact current full source body without a new `read` or reopening a saved result, but any saved read is historical unless it was taken on the current candidate.
- The state does not explicitly provide a top-level “current file hash map”; in this case the hash is available in the patch result.
- The state does not explicitly provide a top-level “current check flags” field; this must be derived from events and the patch-clearing behavior.
- The state does not show physical context-space limits; `calls_remaining` is separate from context space.
- The “ideal correction-cycle” sentence is a design illustration, not a guarantee of remaining capacity.

## Suggestions that need new information or behavior

Some improvements would not be pure presentation:

1. **Explicit `current_file_sha256_by_path`**
   - Currently derivable from the latest relevant result.
   - If the host wants to present it as a stable field, that is new state derivation, though no new tool operation is needed.

2. **Explicit `current_check_flags`**
   - Currently derivable from ordered events plus the rule that patch clears check flags.
   - Presenting it as a host-computed field is new behavior/state, not merely reordering.

3. **Explicit `current_candidate_source_read_complete`**
   - Currently derivable from event sequence and candidate changes.
   - A host-maintained flag would be new behavior.

4. **Showing exact check stdout text**
   - Requires `reopen_result RES-0002`.
   - Not a presentation change.

5. **Showing whether `submit` would be accepted or successful**
   - `submit` only reports the current check flag and does not enforce passing.
   - A success prediction would require new evaluation behavior.

6. **Showing that a future patch is “allowed” because prior read occurred**
   - The patch tool does not inspect read history.
   - Any such presentation would be an actor-facing obligation, not a tool guard.

## Why this presentation helps

The current state already contains the necessary facts, but they are distributed across:

- current candidate,
- current P0,
- ordered events,
- result bodies,
- tool contract,
- response format,
- resource state.

The useful change is to surface a stable block that says:

- This is the current candidate.
- This is the file guard for the current candidate.
- This check was on an older candidate.
- This read was on an older candidate.
- These handles recover exact saved payloads.
- `check` executes; `reopen_result` retrieves.
- `submit` binds to the current candidate but does not enforce a passing check.

That makes the next decision easier without changing the operations, protections, recovery model, ordered event model, or one-action-per-invocation constraint.
