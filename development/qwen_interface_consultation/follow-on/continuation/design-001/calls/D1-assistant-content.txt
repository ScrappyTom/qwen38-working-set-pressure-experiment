I would keep the current interface, but I would make the next-action-relevant facts visible as a compact **operating contract** plus a **decision ledger**, with the raw event frame retained below them as exact evidence. The main design problem is not the data; it is that the operation grammar, binding meanings, recovery semantics, and pre-mutation evidence are currently dispersed across the raw state and the hidden final-action grammar.

The following is a presentation proposal, not an action to execute.

---

## 1. Preferred presentation shape

Keep familiar names and the event frame, but present these first:

1. **Operating contract**  
   Always visible: action classes, required argument forms, limits, binding meanings, and effects.

2. **Decision ledger**  
   Always visible: current candidate, available actions/checks, one-action rule, required pre-mutation read evidence, patch guards, source residency, and recovery handles.

3. **Exact current source pages**  
   Visible when already resident in the current input; clearly separated from metadata.

4. **Saved-result access index**  
   For non-resident or previously read payloads: handles, scope, and the warning that reopening is access, not new execution.

5. **Raw event/audit trail**  
   Full ordered event frame, exact pair identities, hashes, schema versions, and verification details remain available as audit material, but not the primary decision surface.

---

## 2. Concrete proposed tool description

This would remain visible to the operating model. It would not replace the final-action grammar, but it would mirror the implemented facts so they are not hidden only in `response_format`.

### Proposed visible tool description

```text
Next-action surface
====================

Exactly one action may be chosen per invocation. Extra keys are rejected.
The current candidate is bound through expected_candidate_id where required.

A. Inspect current candidate
----------------------------
- p0_page(path, offset)
    Task-independent structure/signature page.
    path is candidate-relative; "." means repository root.
    offset is zero-based.
    Returns directory structure or Python symbol signatures/ranges.
    Never returns exact source.

- tree(path, offset, limit)
    Shallow deterministic candidate-relative directory page.
    path "." means repository root.
    offset is zero-based; limit is 1..16.
    Does not count as exact source read.

- search(path, query, offset, limit)
    Literal case-folded current-source search.
    query is 1..128 characters and within the host UTF-8 byte limit.
    Returns path, line number, and bounded line text.
    Does not count as complete source read.

- read(path, start_line)
    Exact current source whole-line page.
    path is candidate-relative.
    start_line is one-based.
    Returns exact current file hash, returned line range, next_start_line,
    and complete flag.
    complete=true means this page reaches EOF; it does not by itself prove
    that all earlier lines were previously read.
    Reading does not mutate source.

B. Reopen saved custody
------------------------
- reopen_result(handle)
    handle must be a saved result handle, e.g. RES-0001.
    Returns the saved exact operation result JSON envelope, including
    original status/version fields and the original exact body.
    This is retrieval, not a new read.
    It does not extend current-source read coverage.
    It does not rerun checks or mutate source.

- reopen_event(handle)
    handle must be a saved event handle, e.g. EVT-0001.
    Returns the saved old/new action payload envelope for that event.
    This is retrieval of historical action fields.
    It does not rerun the event, edit source, or create a new candidate.

- reopen_observation(handle)
    handle must be a listed observation handle, e.g. OBS-0001.
    Returns the saved observation.
    This is retrieval only.

All reopen operations create a new ordered access event retaining the
canonical source address, but they do not make historical payload current,
rerun an operation, mutate source, change check state, or extend read
coverage.

C. Mutate candidate
---------------------
- patch(path, old, new, expected_candidate_id, expected_file_sha256)
    path is canonical and candidate-relative.
    expected_candidate_id must match the current candidate.
    expected_file_sha256 must match the current target file.
    old and new are exact fragments, each within schema and host byte limits.
    old must occur exactly once in the current file.
    Unchanged bytes are rejected.
    An accepted patch creates a new candidate and clears current check flags.

D. Verify and finish
----------------------
- check(check_id, expected_candidate_id)
    Runs the named available check on the expected current candidate.
    Current available check id: public.
    This is a new check execution on the current candidate.

- submit(expected_candidate_id)
    Terminal action.
    Binds the current candidate and ends the task.
    Reports the current check flag.
    Does not enforce a passing check.
```

This part is not internal audit detail. It represents implemented facts: the final-action grammar, argument forms, binding semantics, and operational effects.

## 4. What each proposed part represents

| Proposed part | Existing fact or operation represented | Why it belongs in the visible presentation |
|---|---|---|
| `stage`, `one_action_per_turn` | Current stage and the one-action-per-invocation rule | These are core operating constraints, not audit details. |
| `current_candidate.candidate_id` | `candidate_id`, `latest_transition_binding.candidate_id` | Needed for `patch`, `check`, and `submit` version guards. |
| `available_check_ids` | `available_check_ids` | Determines which `check_id` is usable now. |
| `call_budget` | `resource_state.calls_used`, `calls_remaining` | Shows action allowance without turning it into a semantic guarantee. |
| `operation_classes` | `available_actions` grouped by effect | Preserves familiar names while distinguishing inspection, retrieval, mutation, verification, and submission. |
| `actor_instruction_obligations.exact_source_required_before_mutation` | Task text and `p0_contract.exact_source_required_before_mutation` | Makes the pre-mutation inspection obligation visible while correctly labeling it as an actor/host obligation, not a patch-tool guard. |
| `required_read_evidence.path` | Frozen acceptance set from the active step | Gives the exact paths whose reads are required. |
| `required_read_evidence.event/result` | `event_handle`, `result_body.canonical_source.handle` | Connects the obligation to exact recoverable evidence. |
| `start_line`, `returned_end_line`, `complete` | Read result fields | Shows whether the saved read page reached EOF. With `start_line=1` and `complete=true`, this is whole-file read evidence for that path. |
| `source_text_in_current_input` | `result_body.residency` and presence of `fields.content` | Tells whether exact source is already in the current input or must be reopened. |
| `patch_guard_file_sha256` | `result.file_sha256` | Provides the guard needed for `expected_file_sha256` when patching. |
| `recovery_index.result_handles` | Saved `RES-` handles from event results | Supports exact recovery of saved operation results. |
| `recovery_index.event_handles` | Saved `EVT-` handles | Supports exact recovery of historical action bindings. |
| `recovery_index.note` | Implementation fact: reopen is access, not new payload or execution | Prevents confusing retrieval with new check, edit, or source coverage. |
| `source_residency_summary` | `externalized_payload_through_sequence`, `result_body.residency`, and event result fields | Makes the residency boundary explicit without ranking or reordering the files. |

## 5. What to show together

I would show these together in the main decision surface:

### Current binding

- `stage`
- one-action rule
- current `candidate_id`
- available actions
- available check IDs
- call budget

This represents the version and stage context for the next operation.

### Required pre-mutation evidence

For each required path:

- path
- event/result handles
- line range
- `complete`
- whether exact source is resident in current input
- current file SHA-256 guard

This directly supports the next decision: whether more exact source retrieval is needed, whether a patch guard is available, and whether the pre-mutation inspection obligation is evidenced.

### Operation effects

Especially:

- `read` does not mutate.
- `complete` means EOF for the page, not universal whole-file history.
- `reopen_*` are retrieval only.
- `patch` creates a new candidate and clears check flags.
- `check` runs a new check on the current candidate.
- `submit` ends the task and reports, but does not enforce, the check flag.

This part preserves the distinction between retrieving saved material and executing a new check or edit.

## 6. What to leave available on request

I would keep these available but not force them into the primary decision surface:

### Exact source pages that are already resident

For the seven resident reads, the exact source text is already part of the current input. I would not hide that if it is already resident, because it is necessary for forming exact `old` fragments. It should be clearly labeled as exact source, separate from metadata.

However, if the interface chooses to externalize source pages for context management, that externalized page should be represented by:

- path
- event/result handle
- line range
- file hash
- complete flag
- reopen handle

### Non-resident saved result bodies

For `RES-0001` through `RES-0004`, the exact source text is not resident in the current input. These should be available through `reopen_result`, and the decision surface should say so.

### Full raw event frame

The full `active_phase_event_frame` should remain available because it preserves ordered activity and exact evidence. But after the decision ledger, it can be secondary.

### Full JSON schema

The final-action grammar can remain the validator. The visible operating contract should mirror required keys, limits, and effects, but the full schema does not need to dominate the prompt.

## 7. What remains internal audit detail

These can remain in the audit trail without being primary decision signals:

- `schema_version` values
- `event_frame_verification` booleans
- `exact_pair_identity` SHA/size for each complete action/result pair
- `canonical_payload_reuse_events`
- `external_payload_records` and `resident_payload_records` as raw counts
- `event_prefix_sha256`
- `seed`
- `fixture_id`
- `semantic_ranking:false`
- `host_sufficiency_judgment:false`
- `one_action_result_identity_per_sequence`
- `opaque_handle_is_not_the_progress_signal` as a raw internal flag
- detailed `resident_signal_contract` internals

Some of these are important for custody, ordering, or verification, but they are not needed to choose the next action. The decision view should instead surface their practical consequences: handles exist, source is resident or externalized, result is complete, and candidate/file bindings are available.

One exception: the practical rule “reopen is access, not new payload” should remain visible in the recovery section, even if the internal flag names are not shown.

## 8. Preferences versus implementation facts

### Preferences

- Group actions by effect rather than only by raw available list.
- Put required-read evidence next to patch guards.
- Show “actor obligation” separately from “tool enforcement.”
- Keep exact source text visually distinct from metadata.
- Avoid recommending a specific next action; present available operation classes and evidence.

### Implementation facts

- One action per invocation.
- `patch` requires `expected_candidate_id` and `expected_file_sha256`.
- `patch` creates a new candidate and clears check flags.
- `read.complete` means page reaches EOF.
- `p0_page`, `tree`, and `search` do not count as complete source reads.
- Reopen operations return saved envelopes and create ordered access events.
- Reopen does not extend current-source read coverage.
- `submit` reports current check flag but does not enforce a pass.
- `expected_candidate_id` and file hashes are version guards.

### Uncertainties

- The state does not show whether `check public` has already been run or passed. It only shows that `public` is available.
- The state does not show the actual regressions or whether a patch is required.
- The state does not show current file hashes for files not covered by a read result.
- The root `repository_complete:false` means the P0 root is not repository-complete; it does not by itself identify missing required reads.
- The `complete` flag alone is not a whole-file guarantee unless paired with the returned line range and start position. Here, `start_line=1` plus `complete=true` gives whole-file read evidence for each required path.

## 9. Suggestions that would require new information or behavior

These are not pure presentation improvements unless explicitly limited to derived views from existing fields:

1. **A single `required_reads_complete: true` boolean**  
   This can be presentation if derived from the existing event frame: all required paths have `start_line=1`, `complete=true`, and `next_start_line=null`.  
   But if the tool or host uses it to enforce mutation, that is new behavior. The patch tool does not currently inspect read history.

2. **A “check public passed” field before running check**  
   This would be new information. The current state only shows that `public` is available.

3. **Current file hashes for all files without reads**  
   This would be new information. Only show file hashes from actual read results or other current-source evidence.

4. **Recommended next action**  
   This would be new inference or ranking. The interface should show available actions and evidence, not rank or choose for the model.

5. **Patch-side enforcement of read-before-mutation**  
   This would be new tool behavior. The stated design treats read-before-mutation as an actor/host obligation, not a patch guard.

6. **Showing hidden test files or repository completeness beyond the frozen set**  
   The task gives a frozen acceptance set. Expanding that set would be new task interpretation, not presentation.

7. **Guaranteeing remaining capacity for the ideal correction cycle**  
   The correction-cycle sentence is a design illustration. `calls_remaining` is real; an ideal cycle guarantee is not an implemented recovery guarantee.

---

## 10. Why this presentation helps without changing operations

The current state already contains the necessary facts:

- The required paths are in the active step.
- The required reads are evidenced by `EVT-0001` through `EVT-0011`.
- The exact result payloads are bound by `RES-0001` through `RES-0011`.
- The current candidate is `2355...`.
- The available check is `public`.
- The source residency boundary is visible through `result_body.residency`.
- The patch guards are visible through `result.file_sha256`.
- The operation grammar is implemented and available, but currently less visible than the raw event frame.

The preferred change is therefore not a new memory architecture or a new tool. It is a better presentation of the same facts:

- show the operating contract;
- group candidate, check, read evidence, patch guards, and recovery handles;
- keep exact source separate from metadata;
- keep raw custody hashes and ordered event details available as audit evidence;
- never allow retrieval to be presented as execution;
- never allow actor obligations to be confused with tool-side enforcement.
