## 3. What `reopen_result` with `RES-0001` would return, and what would not change

A `reopen_result` action with:

```text
handle: RES-0001
```

would be expected to return the saved result envelope for that handle. Operationally, that envelope would contain:

- `accepted`: expected to be true for a valid available handle
- `handle`: `RES-0001`
- `exact_result_utf8`: the full saved original result JSON for that read result
- `exact_result_sha256`: the hash of those saved result bytes
- `size_bytes`: the size of those saved result bytes

The important part is `exact_result_utf8`: it is the **full saved original read result**, including the original result fields and the exact body that was returned for the read. In this case, that means the saved read result for `saved_runs.py` from sequence 1.

It is not merely the current metadata visible in the state.

### Full saved result vs. extracted-field metadata

In the current state, the `result_body` for `RES-0001` shows:

- `present: true`
- `residency: "external"`
- `fields: null`
- `field_names: ["content"]`
- extracted-field payload hash:

  ```text
  76a8b2d40bb9f6ac52e4f8bb1adcd105f5029b2d80d189e840cf972ec8ba6bd4
  ```

- extracted-field payload size:

  ```text
  10164
  ```

That hash and size describe the **extracted content-field payload only**. They do not describe the raw file bytes, and they are not necessarily the hash/size of the full saved result returned by `reopen_result`.

By contrast:

- `file_sha256` describes the source file bytes.
- `exact_pair_identity` describes the complete action/result pair in the event frame.
- `exact_result_sha256` from `reopen_result` describes the saved original result bytes being returned.
- `exact_result_utf8` contains the saved result JSON itself.

So `RES-0001` currently appears in the input as an externalized payload reference; reopening it would return the saved exact result payload behind that reference.

### What would change

If the action were executed:

- A new ordered access event would be created.
- The state’s event sequence/counter state would advance.
- The call counters would reflect one more action.
- The new event would retain the same canonical source address, i.e. it would be an access to the same saved payload rather than a new payload.

### What would not change

It would not:

- modify the candidate
- modify `saved_runs.py` or any other source file
- change the file hash
- change the current candidate identity
- rerun the `read` operation
- make the saved source “current” in the sense of replacing current source state
- extend current-source read coverage
- alter check flags, patch state, or submission state
- modify the original saved `RES-0001` payload

In short: `reopen_result` is retrieval of a saved exact result, not mutation, not re-reading, and not a new semantic source event.
