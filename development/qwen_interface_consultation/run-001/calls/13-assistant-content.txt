## What the two `expected_*` arguments refer to

### `expected_candidate_id`

This is a precondition binding on the **candidate being patched**.

It says:

> Apply this patch only if the current/authorized candidate is this exact candidate.

In the supplied state, it matches the current `candidate_id` and the `candidate_id` from the prior `read` result. It is not the ID of a future candidate; it is the expected predecessor candidate.

### `expected_file_sha256`

This is a precondition binding on the **exact current contents of `service.py` in that candidate**.

It says:

> Apply this patch only if the file `service.py` in the expected candidate currently has this SHA-256.

In the supplied state, it matches the `file_sha256` returned by the previous `read`:

```text
5d080563b57287276f589c2b2714ef499269efe7405a288b3c1474f5a92bf271
```

Important: this is the **pre-patch** file hash, not the hash of the file after the patch. It is also not the `canonical_source.sha256` from the event result; it is the file-content hash reported by the read result.

Together, these arguments act like optimistic-concurrency guards:

- `expected_candidate_id` prevents patching the wrong candidate.
- `expected_file_sha256` prevents patching a file whose contents have changed since it was read.

## When the tool would reject it

The tool would reject the patch if the stated preconditions no longer hold or the replacement cannot be applied exactly. Based on the supplied state, the main rejection conditions would be:

1. **Candidate mismatch**  
   Reject if the current candidate is not:

   ```text
   f698835a3877ac7f0e7b37aac6d472a35e1b481894d52eee51463eb253308377
   ```

   For example, if another `patch` had already created a new candidate, this stale `expected_candidate_id` would fail.

2. **File hash mismatch**  
   Reject if the current SHA-256 of `service.py` in that candidate is not:

   ```text
   5d080563b57287276f589c2b2714ef499269efe7405a288b3c1474f5a92bf271
   ```

   For example, if the file was modified after the read, the expected hash would no longer match.

3. **Path not applicable**  
   Reject if `service.py` is not an existing patchable file in that candidate, or if the path is invalid/out of scope.

4. **Replacement cannot be applied exactly**  
   Reject if the literal `old` text:

   ```text
   return 1
   ```

   is not present in the current file contents in the way required by the tool’s exact-replacement semantics.

   In the current visible state, `return 1` is present once. If the tool requires a unique exact occurrence, this patch would pass that condition as long as the state remains unchanged. If the tool allowed multiple occurrences and replaced all of them, the visible result would still be the same here because the occurrence is unique.

5. **General tool constraints**  
   Reject if some broader action precondition fails, such as call-limit exhaustion, terminal/submitted state, invalid payload, or stage restrictions. The supplied state does not indicate that any such condition is currently true.

The operation would **not** be rejected merely because `check public` has not yet been run, and it would not be rejected merely because the file currently returns `1`. Those are task/workflow considerations, not patch preconditions shown in the state.
