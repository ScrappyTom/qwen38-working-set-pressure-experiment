## Preserved smoke failures and the extra controls

The first ordinary reply passes. The first literal reply is well formed but omits
the requested trailing LF. Direct input inspection shows that the pinned template
trimmed that LF from the end of the supplied example. The second literal fixture
puts the example between explicit markers so its trailing LF survives rendering;
the returned literal still lacks LF. Its reasoning says it will include LF, but
that statement is not evidence of the generated byte.

One further control uses the same clarified prompt and a grammar that requires the
exact supplied final. It returns the LF correctly, with identical thinking and
exactly one additional generated token. This establishes that the endpoint and
host decoder can preserve the byte. It does not justify silently appending source
bytes or claiming that unconstrained copying is exact. Literal edits continue to
mean the actual emitted source; successor checks assess the resulting work.

Both failed assertions, original inputs and all four complete responses remain
preserved. The plan's initial two smoke calls therefore expanded by two diagnostic
controls during the authorized repair, before the task rerun. Total qualification
inference is 507 input tokens, 1,174 generated tokens and 59.592 request seconds;
see TRANSPORT_METRICS.json. All four calls end normally. No task attempt was retried.

The failed smoke seals' `completion_requests` field counts verified cases because
the inherited helper received `len(rows)` after assertions. It is 1/0 rather than
the actual 2/1 requests in those two folders. The complete invocation/response
custody records establish the counts above. Preserve the erroneous derived fields;
do not use them as inference totals.
